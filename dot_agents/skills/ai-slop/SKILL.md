# AI Slop Policy

It is our strict policy that any AI slop, which is defined as text or code generated by an LLM, must never be presented
to other humans as if it were human-authored. Today we do not have built-in mechanisms in our systems of record to
distinguish between "anelson wrote this" and "anelson's clanker wrote this". Therefore we must take care to be explicit
about the provenance of AI-generated content whenever posting that content under the user's name.

How we do that depends very much on the format and the medium.

At all times, AI slop or otherwise, always adhere to the VOICE guidance provided earlier in the prompt.

## Code in source code files

In general, code written to source code files does not require any explicit provenance statement. Provenance is
documented separately from the code itself. Any acknowledgement of AI provenance (or human provenance for that matter)
would only serve as a distraction.

## GitHub-flavored Markdown

Pull requests, Github issues, and comments thereon all support Github-flavored Markdown (GFM). When posting content to
these systems (typically using `gh` but the actual mechanism is irrelevant here), our convention is that the provenance
is made explicit by putting the entire content inside a `<details>` block, with a `<summary>` set to "AI Slop: "
followed by a summary of the contents of the block consisting of not more than 12 words.

When creating an issue or a PR, the title should be composed normally, try to make it meaningful without being too long,
and do not invent stupid conventions like a prefix or suffix or some annotation that is inconsistent with the rest of
the issues/PRs in the repo.

The _SOLE_ exception to the <details> block rule is when creating a PR what references corresponding issues with "Closes
#XXX" or "Fixes XXX" notation. Github explicitly recognizes those when they appear on a line by themselves, and that is
information that we do not consider to be AI slop, so that should be placed outside of the `<details>` block, before it.

When posting content in GFM, make use of the rich formatting it provides to improve readability. Use `fixed width`
formatting for code blocks, type and file names, and names of packages. Use other Markdown as appropriate for
readability.

USE OF EMOJI IS STRICTLY PROHIBITED!

Bulleted lists are a useful way to present some kinds of information, but do not add the LLM tic in which each bullet
point has a few bolded words followed by the rest of the bullet point in a normal weight. This is distracting and
counterproductive.

## Git commit messages

See /commit for general guidance on commit message structure and contents. Unfortunately the Git commit message format
doesn't provide the same formatting luxuries, so we must resort to a convention-based approach to marking AI provenance.

The first non-blank link after the commit title must be:

```
BEGIN AI SLOP
```

At the end of the commit, add one more blank line followed by:

```
END AI SLOP
```

For long or complex commit messages, using headings is a worthwhile way to organize the content. But the normal
Markdown `#` heading syntax is unsuitable for commit messages, as the `#` prefix is treated as a comment and stripped
out of the commit message when I edit it with `git commit --amend`. Therefore, use the alternative syntax of `=`
characters on the line after the header line, with the number of `=` characters denoting the heading level.

## Exceptions

The purpose of this skill is to clearly make AI slop in places where other humans are likely to encounter it. None of
this applies to content that I have requested for myself, as I obviously know that it's slop. This includes one-off
HTML reports or dashboards, explainers, research or plan or design Markdown files, and the like.
